Executive Summary

HTTP forces every endpoint into "client" or "server" — DHttp removes that distinction.

1 · DQuic

Rust-native QUIC extension with built-in multipath NAT traversal. No external STUN/TURN cluster required.

2 · DDns / E-Record

A new DNS record type (RTYPE 266) that resolves a name to a full reachability tuple, not just an IP.

3 · DHttp

HTTP/3 extended to use server-initiated bidirectional streams, so any endpoint can push as well as pull.

Edge device → stable name alice.smith~ + certificate-backed identity + public HTTPS-style URL ZERO cloud relay in the steady-state data path

The Paradigm Shift

An old problem, repeatedly re-solved badly

  • 1994 · RFC 1918: private IPs + NAT break global routability
  • 2000s · VPNs & tunnels: Tailscale, WireGuard, ngrok — private overlays, still siloed from each other
  • 2020s · Agent frameworks: MCP / A2A's typical deployment model assumes a publicly reachable server — pushing physical and local-first tools to the margins
  • 2020s · Chat-app bridges: Telegram/WhatsApp bots as ad hoc RPC for laptop agents

The inflection point

Agentic AI needs bidirectional, low-latency, cross-network calls to physical endpoints — robots, home sensors. Point-solutions don't compose.

Status Quo & Bottlenecks

Routing through a cloud intermediary reintroduces the bottleneck

  • connect() — nearly universal
  • listen() / accept() — servers only, because it requires global routability
  • Cloud-relay pattern: agent → broker/chat API → device

Concrete costs of the relay pattern

  • Every message round-trips through a third party (latency + $ per request)
  • The relay operator can read, store, or lose your data
  • A robot/camera effectively "phones home" through infrastructure it doesn't control

Why Existing Architectures Fail

The failure is structural, not incidental

  • Root cause: IPv4 exhaustion → NAT → loss of universal listen() → HTTP inherits the client/server split (RFC 9110 §3.3)
  • VPNs: fix routing within a boundary, fragment the internet further (N VPNs = N silos)
  • MCP: typical deployments assume servers with public, fixed IPs — excluding laptop/embedded unless tunneled
  • OAuth/OIDC: solves delegated login to a platform, not mutual serverless identity between two endpoints

Common thread

Every fix operates one layer above the actual break (routing) — so none of them actually restore global reachability.

Introducing DHttp

"HTTP, but every endpoint can also be the server."

Not a new protocol competing with HTTP — it's HTTP/3 with the client/server role restriction removed, over a QUIC extension that natively handles NAT traversal and identity.

Preserves: HTTP semantics, URL structure, request/response, TLS-grade security Removes: the requirement that only globally-routable hosts accept connections
DHttpApplication — HTTP/3 with server-initiated bidirectional streams
DDns / E-RecordNaming — resolves a name to a full reachability tuple
DQuicTransport — P2P QUIC + NAT traversal + multipath
alice.smith~ ≡ alice.smith.dhttp.net The trailing ~ is a root-suffix alias: type the short form in any DHttp-aware client and DNS resolution does the rest. Endpoints that live on the LAN resolve first via ._dhttp.local (mDNS) before any public route is consulted.

Core Technology 1 · DQuic (P2P Transport)

STUN, Relay, and Signal folded into the QUIC packet itself

  • ep / &EP model: private ep pairs with a public delegate &EP; packets to &EP forward to ep
  • Any public node with full-cone NAT can be an &EP — community-contributed, DePIN-style
  • Traversal inside the connection: ADD_ADDRESS, PUNCH_ME_NOW, REMOVE_ADDRESS

Multipath — up to 8 concurrent paths

One logical connection runs over cellular IPv4, WiFi IPv4, cellular IPv6, WiFi IPv6.

  • Priority: direct > relayed · LAN > WAN · WiFi > cellular · IPv6 > IPv4
  • vs Happy Eyeballs: negotiates all paths under one connection ID — no wasted handshake, no discarding a slower-but-preferred IPv6 path

Core Technology 2 · DDns / E-Record

Naming rights for every device, not just servers

E-Record (RTYPE 266): rtype(266) | flags(8 bits) | rdata

bit 1 · addr family
bit 2 · primary/backup
bit 3 · single/cluster
bit 4 · NAT + &EP
bit 5 · load info
bit 8 · signed

Self-reporting, self-signed

  • Endpoint detects its reachable address and republishes its own signed E-Record — no DNS console, no ops, no spoofing (bit 8)
  • Namespace: .dhttp.net (shorthand ~) — sub-zones .home~, .robot~, .svc~, .car~
mDNS firstsame-LAN: ._dhttp.local — zero added latency, zero public traffic
▼ fallback when unreachable locally
DDns publiccross-network: name.dhttp.net E-Record → full reachability tuple
▼ only if no local hit
P2P connectDQuic NAT traversal toward the chosen path

Core Technology 3 · Unified Identity & Access Control

One artifact — name + keypair + certificate

Unified Identity = name + public/private keypair + certificate, verified via mutual TLS at connection time.

Legacy: IP (not verifiable) · password (not callable) · token (not signable) · OIDC (login, not device identity)

Deny-by-default ACLs, keyed to identity, not IP

  • Default: no external access unless allowed
  • Default: local (dhttp.local) allowed · self-access allowed
  • Imprinting: first-ever visitor becomes the administrator — only on a verified bootstrap channel
  • Admin extends allow-list to specific names or "anyone"
  • Authorization header repurposed for third-party-issued, signed, time-bounded credentials (Secretary, Student, Citizen)
Safe-by-bootstrap: imprinting never happens blind

Imprinting is only accepted over a channel already proven to be the operator's, not an attacker's. The three eligible bootstrap contexts: physical proximity (out-of-band QR / NFC pairing), same-LAN local context (._dhttp.local via mDNS), or out-of-band identity verification (comparing a printed/displayed public-key fingerprint). A random first-contact from the open internet is never auto-promoted to administrator — this blocks MITM "first-contact takeover" in untrusted / coffee-shop networks.

Scalability & Reliability

Reliability comes from path diversity, not a bigger cluster

  • Failure modes: single-path drop with auto-failover; delegate &EP going offline mid-session; DNS/DDns propagation during mobile handoff
  • Delegate availability: DHT-based tracking of candidate &EP nodes; register with several delegates simultaneously for redundancy

Load-shedding (Pishoo forward)

Any node caps donated relay/STUN/Signal capacity: off / light / medium / large / xlarge / xxlarge / auto / unlimited.

No single point of failure — by design, vs a centralized relay cluster (single organizational point of failure even if technically redundant).

Open Source Strategy

Neutral infrastructure can't be owned by one vendor

  • Licensing: Apache-2.0 across DQuic, DDns ref implementation, SDKs — permissive, patent grant included
  • Governance: submit DQuic NAT-traversal + E-Record through IETF draft → RFC, the same path QUIC took
  • Commitment: no feature affecting interoperability (identity, ACL semantics, wire format) will be held back for a paid tier

Open-core boundary (stated plainly)

Protocol, transport, naming, and reference gateway (Pishoo core) are fully open. Commercial offerings are optional managed conveniences layered on top — not gated protocol features.

21 / 30
Ecosystem Compatibility

Sits underneath existing frameworks — doesn't replace them

  • MCP servers: run behind Pishoo instead of requiring a public-IP host; tool discovery unchanged
  • A2A / LangChain-style: agent identity → Unified Identity; inter-agent calls become direct DHttp requests
  • ROS2 / robotics: DHttp as a WAN bridge for LAN-only ROS2 topics, reusing E-Record naming
  • AnySee browser: drop-in DHttp-aware client; falls back to normal HTTP for non-.dhttp.net names

Compatibility posture

No rewrite of application logic required — only the connection/listener layer changes, since HTTP semantics are preserved.
