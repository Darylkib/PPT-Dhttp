Part 1 · Background

HTTP's asymmetry: servers are findable, clients are not

  • listen() needs a routable address + open port — so only cloud hosts qualify as "servers"
  • HTTP inherits the transport's reachability; the request/response split is baked into the spec
  • Bidirectional needs (SSE, WebSockets) still terminate on a fixed, reachable server — the model never changed
  • In HTTP/3 the asymmetry is deeper: streams are client-initiated, and every device behind NAT is permanently a client

The consequence

  • Your laptop can open connections to almost anything — but accept almost none
  • The standard fix today: give a third party in the middle standing access to that traffic
RFC 9110 §3.3: HTTP assumes a single, addressable originEven HTTP/3 kept the client/server split
04 / 30
Part 1 · Background

1994 rewired the internet's topology — we never fixed it

  • 1994 · RFC 1918: private IP space + NAT end global routability
  • NAT lets endpoints originate traffic but not accept it; carrier-grade NAT pushed the same wall into the ISP
  • "Reachability" quietly became a synonym for "buy a cloud host with a public IP"

What was lost

Universal reachability: the pre-1994 property that any device could reach any other device. Today's internet is de facto client/server — only servers are reachable, and there's no standards-track path back.

05 / 30
Part 1 · Background

Every workaround goes around the break, not at it

Overlay VPNs — Tailscale / WireGuard

  • Fix reachability inside a membership boundary: N VPNs = N silos that still can't reach each other
  • Control-plane dependence: coordination servers and key exchange remain a cloud to trust
  • Every new viewer = another install + join, all over again

Cloud relays — ngrok and friends

  • Every byte of traffic flows through the relay provider's cloud
  • Added latency on every request, in both directions
  • Per-request cost + vendor lock-in = a tollbooth on your data path
Result: silos, extra latency, and cloud dependency — never the removal of the third party
06 / 30
Part 1 · Background

OAuth is a login protocol — agentic AI just hit the wall behind it

  • OAuth/OIDC solves "log me into your platform," not "let two arbitrary devices mutually authenticate without a platform"
  • MCP and A2A's typical production deployment models assume a publicly reachable server, excluding local-first and physical edge tools
  • An agent that controls a robot can't hand write-access to a stranger's cloud — yet every broker pattern defaults to exactly that

The inflection point

Agentic AI is the first mainstream workload where "route everything through a cloud broker" is disqualifying — and whoever "solves" it as a proprietary relay just becomes the next seized chokepoint. It has to be an open protocol.

Part 1 · Summary

Three compounding costs of the workaround stack

Silos

Private overlays fragment the internet further: every VPN membership, every relay provider, is one more wall between endpoints that should talk directly.

Latency

Cloud relays add a mandatory hop through a third party — per request, in both directions — exactly where you'd rather not be.

Cloud dependency

Whoever is in the data path gets read-access by default. Today that's your traffic; for devices with hands and feet, it's write-access to the physical world.

The pattern: every patch (VPN, relay, OAuth-issued tokens) adds a boundary or a dependency — none of them remove the third party. Time to fix the layers themselves.

Part 2 · Solution

DHttp = HTTP/3 with one restriction removed

  • Role symmetry: either endpoint can open streams — agent and device both push and pull over the same connection
  • Transport — DQuic: QUIC extended with native multipath NAT traversal (no STUN cluster)
  • Naming — DDns / E-Record: a name resolves to a reachability tuple, not just an IP
  • Identity & authorization: name + keypair + cert, mutually verified at the handshake; Pishoo enforces default-deny ACLs

The output

  • Every edge device gets a name, a certificate, and an HTTPS-style URL any authorized peer can reach directly (walle.robot.dhttp.net)
  • No public IP required · no relay in the steady-state path
  • DHttp-unaware clients still work — plain HTTPS against the public-facing name

Part 2 · Pillar 1

DQuic — P2P is built into the QUIC packet, not bolted on

  • ADD_ADDRESS / PUNCH_ME_NOW frames coordinate hole-punching via peer-contributed &EP delegate nodes — no dedicated STUN cluster
  • Connections are identified by connection ID, not socket tuple: a connection survives a network change with no reconnect
  • Builds on the IETF QUIC NAT-traversal draft — the same incremental path QUIC itself followed

Multipath by default

  • Up to 8 concurrent paths per connection
  • Priority: direct > relayed · LAN > WAN · WiFi > cellular · IPv6 > IPv4
  • Warm failover — drop a path, keep the connection ID

Part 2 · Pillar 2

DDns / E-Record — a name is more than an IP

  • RTYPE 266 publishes a reachability tuple: IP + port + optional &EP delegate + self-signature (flags bit 8)
  • The device re-publishes its own signed record on every network change — no DNS console, no static IP, no provisioning call-home
  • A name is an address, not a credential: even E-Record poisoning buys nothing once sessions pin the peer certificate

Part 2 · Pillar 3

Identity is a keypair; access is an explicit list

Unified Identity

  • Name + keypair + certificate, verified mutually at the QUIC/TLS 1.3 handshake
  • Possession is authority — nothing central to steal or subpoena

TOFU — but never over the open internet

  • First contact imprints only over a channel that already proves ownership: physical proximity (QR/NFC), same-LAN mDNS, or out-of-band fingerprint check
  • A random internet first-contact is never auto-promoted to administrator
Why the constraint?

Otherwise a coffee-shop MITM could "imprint" first and walk away with the keys. TOFU is safe only when the bootstrap channel already binds the human and the device.

Part 3 · Technical Advantages

One endpoint, both directions — in Rust

Server-initiated bidirectional streams on a device with no public IP:

// device side — walle.robot runs Pishoo; no router config, no public IP
use dhttp::{Endpoint, Identity, ServerInitiated};

let dev = Endpoint::new("walle.robot~")
    .bind(Identity::load("device.pem").await?);          // mTLS identity

dev.on("/task/clean", |ctx| async move {
    ctx.request_body().await?;                                      // peer's push
    let mut push = ctx.push_stream().await?;                 // server-initiated
    push.write_all(b"stream: cleaning-logs\n").await?;  // either side flows
    Ok(())
}).await?;

// caller side — an ordinary HTTPS-style URL, from any network
let resp = dhttp::get("https://walle.robot~/status").await?;
The same HTTP semantics agents already use — the only change is who can initiate a stream

Part 3 · Technical Advantages

Access control is one CLI line

$ cargo install dhttp-cli
$ dhttp identity create
$ dhttp access "/shell" allow "bob.lee~"
$ dhttp access "/demo-a" allow "james.wilson~"

  • No router configuration · no tunnel · no dashboard token to copy
  • Revoke in one line too: dhttp access "/shell" deny "bob.lee~"

Part 4 · Ecosystem

Open at the core, sustainable at the edge

  • Dual-licensed Apache-2.0 / MIT across DQuic, the DDns reference implementation, and the SDKs (Rust, Python, JS/TS)
  • IETF draft submission: DQuic NAT-traversal + E-Record go through the draft → RFC path — the same route QUIC itself took

Open-core boundary, stated plainly

Protocol, transport, naming, and the reference gateway are fully open. Commercial offerings are optional managed conveniences layered on top — never gated protocol features.

Part 4 · Ecosystem

Sits underneath your stack — it doesn't replace it

  • MCP servers: run behind Pishoo instead of requiring a public-IP host; tool discovery is unchanged
  • A2A-style agents: agent identity becomes Unified Identity; inter-agent calls become direct DHttp requests
  • ROS2 / robotics: DHttp as a WAN bridge for LAN-only topics, reusing E-Record naming
  • Nginx-shaped operations: Pishoo config mirrors nginx (server{}, location{}, proxy_pass) — no new operational model

Compatibility posture

No rewrite of application logic. Only the connection/listener layer changes, because HTTP semantics are preserved end-to-end. DHttp-unaware clients fall back to plain HTTPS on the public-facing name.

Part 4 · Ecosystem

Public review before protocol changes land

RFC-style process

  • Wire-format, flag, and header-semantics changes need a public design doc + review period before merge
  • Security-relevant changes (identity verification, ACL default-deny) get mandatory external review
  • Path to multi-maintainer or foundation-style custody of the spec as it grows

Special Interest Groups

  • SIG-Transport — DQuic / NAT traversal / multipath
  • SIG-Naming — E-Record / DDns / resolution
  • SIG-Gateway — Pishoo edge runtime
  • SIG-SDK — Rust · Python · JS/TS bindings
